# 绿蓝黄数据链路白名单台账

## 1. 目的

本台账用于对齐公司三色安全分区之间的数据链路白名单，确保经过边界的数据都可审批、可管控、可审计、可回滚。

2026-07-28 用户确认：当前蓝、黄两台服务器已在四层网络限制为双方登记的 IP 和端口互访；本仓库当前阶段不使用 mTLS。2026-07-30 七层能力扩展为精确 Host/接口白名单以及请求、响应 JSON schema 过滤。2026-07-31 用户提供的现场配置确认：蓝 WAF `10.64.5.4:80`，黄 WAF `10.64.9.2:80`，业务 Host 为 `kb.pxsemic.tech` 和 `kb-1.pxsemic.tech`，黄端两条路由都指向 `192.168.14.249:6789` 并发送后端 Host `kb.pxsemic.tech`。2026-08-04 用户提供新的黄区知识库五接口文档，活动白名单据此扩展为检索、资产详情、知识库健康、只读图谱查询和图谱健康接口。具体四层 ACL 记录、来源系统身份、owner、QPS 和放行审批仍未收齐，现场上线时必须核对。

本台账覆盖：

- `绿 -> 蓝`：互联网侧需求、任务和企微消息进入蓝区。
- `蓝 -> 绿`：蓝区任务状态通过 `114服务器 -> 智伴` 回传绿区。
- `蓝 -> 黄`：蓝区向黄区下发任务、同步 Git 或访问受控服务。
- `黄 -> 蓝`：黄区代码、数据、文档脱敏后通过 OpenClaw-to-OpenClaw 传给蓝区。
- `绿 -> 黄`：企微 Channel 知识查询等特殊跨级链路。
- OpenClaw 控制面 `18789`：跨区禁止，不进入业务白名单。

## 2. 三色分区定义

| 分区 | 定义 | 控制口径 |
|---|---|---|
| 黄区 | 完全的环境隔离，只可以开放某些通道连接其他区 | 最严，默认不通，按通道逐条审批 |
| 蓝区 | 在黄区安全策略之上，额外增加大模型访问能力 | 承载 OpenClaw、大模型访问和跨区协同能力 |
| 绿区 | 完全的互联网访问，只有少数内容无法访问 | 最开放，所有进入受控区的数据必须标记来源并审计 |

隔离强度：黄区 > 蓝区 > 绿区。

## 4. 白名单台账字段

每条生产白名单必须补齐以下字段，缺任一关键字段都不能放行：

| 字段 | 要求 |
|---|---|
| 白名单 ID | 使用稳定编号，例如 `GB-001`、`YB-001` |
| 方向 | 明确 `绿->蓝`、`蓝->绿`、`蓝->黄`、`黄->蓝`、`绿->黄` |
| 边界 | 明确跨越哪个安全边界 |
| 源系统 | 写清系统名、分区、来源身份、源地址或来源网段 |
| 目标系统 | 写清系统名、分区、目标地址、端口、服务名 |
| 协议端口 | HTTP、HTTPS、WSS、Git、企微回调等 |
| 来源/身份控制 | 四层 ACL 的源/目标地址和端口；如业务另有 API Key、签名或服务账号，同时记录管理归属 |
| 接口白名单 | host、path、method、callback 路径、Git remote、WSS path |
| 数据白名单 | 允许字段、消息类型、文件类型、内容等级 |
| 禁止项 | 明确禁止字段、禁止文件、禁止原文、禁止控制面 |
| 脱敏要求 | 黄区出区前的脱敏规则、扫描方式和审批方式 |
| 大小和频率限制 | 单条大小、附件大小、批量条数、QPS、回调频率 |
| 审计字段 | request_id、task_id、源身份、目标身份、rule_id、数据摘要 hash |
| 责任归属 | 业务 owner、运维 owner、安全审批人、工单、有效期、复核周期 |
| 验证方式 | 放行用例、拒绝用例、日志查询方式、回滚方式 |

## 5. 知识流动分级

| 级别 | 内容 | 跨边界策略 |
|---|---|---|
| K0 | 无敏感信息的状态数据 | 可蓝->绿回传，但必须字段白名单化 |
| K1 | 低敏摘要、任务进度、错误码 | 可跨边界传输，限制长度并记录 task_id |
| K2 | 脱敏后的代码、数据、文档片段 | 仅黄->蓝允许，必须脱敏、扫描、记录 hash |
| K3 | 原始代码、原始数据、密钥、凭证、未脱敏文档 | 禁止出黄区，禁止回传绿区 |

## 6. 黄区 -> 蓝区脱敏知识流准入规则

黄区出区材料必须满足以下规则：

1. 数据等级只能是 K2，K3 禁止出区。
2. 传输前必须删除密钥、Token、账号、个人信息、内网地址、未授权业务数据。
3. 文件类型必须在白名单内，默认只考虑文本、结构化摘要、脱敏代码片段和脱敏文档片段。
4. 单条数据必须关联 task_id、工单或需求编号。
5. 通过 OpenClaw-to-OpenClaw 的登记链路传输，不允许另开临时通道。
6. 传输前后记录摘要 hash、源身份、目标身份、时间戳和处置结果。

## 7. 蓝区 -> 绿区状态回传准入规则

蓝区经 `114服务器 -> 智伴` 回传绿区时，只允许传 K0/K1：

1. 允许字段：任务 ID、阶段、成功/失败、错误码、必要摘要、时间戳。
2. 禁止字段：黄区原始代码、原始数据、文档全文、完整模型上下文、密钥、凭证。
3. 错误信息只允许摘要级说明，不能回显黄区原文。
4. 回传消息必须带 request_id 或 task_id，便于从绿区追溯到蓝区和黄区审计。
5. 智伴接口契约、114 服务器所在分区、协议端口和身份凭证补齐前，链路保持禁止生产放行状态。

## 8. 当前仓库 WAF 能力映射

当前仓库提供简化双 WAF 请求过滤能力（不等于现网已部署或任何 URL 已获准）：

- 双节点路径：`10.64.5.4:80` 蓝 WAF 通过普通 HTTP 访问 `10.64.9.2:80` 黄 WAF，再固定访问 `192.168.14.249:6789`；来源、目标 IP 和端口限制依赖现场四层策略。
- 运维配置：精确 Host、method、path、受限末尾 UUID 路径模板、请求 schema 和逐状态码响应 schema 从 `conf/waf_rules.lua` 加载；不同 Host 可登记相同 method/path 和不同契约。
- 固定 Nginx 配置：`conf/nginx-blue.conf`、`conf/nginx-yellow.conf` 已保存上述地址和 `kb.pxsemic.tech` / `kb-1.pxsemic.tech`；部署包直接携带，模板仅供审批后迁移使用。
- 活动白名单：`conf/waf_rules.lua` 登记 `kb.pxsemic.tech` 的 5 个知识库接口；`kb-1.pxsemic.tech` 虽存在于固定 Nginx 配置，但未登记七层规则，默认拒绝。
- `POST /ai/knowledge/search` 只接受必填 `query` 和可选 `top_k`，只返回向量结果；原 `include_graph`、`graph_top_k` 和 `graph_results` 不再属于该接口。
- `GET /ai/knowledge/assets/{uuid}` 只匹配一个末尾规范 UUID 路径段；任意前缀、后缀、额外层级和非 UUID 值拒绝。
- `POST /ai/knowledge/graph/query` 接受文档登记的 `cypher`、`parameters`、`limit`，其中 `cypher` 最长 20000 字符、`limit` 为 `1～1000`；WAF 只做 JSON 结构和范围校验，服务端仍必须保证 Neo4j 账号只读并拒绝写入型语句。
- 四个新增接口的错误状态码和错误 JSON 未在源文档登记，当前只允许其 `200` 响应；未登记状态码 fail-closed 为 `502`。检索接口继续允许已登记的 `200`、`422`、`502`、`503`。
- `results[].metadata`、资产 raw document metadata、Cypher parameters 和图谱 rows 按接口文档允许动态字段，属于对“未登记字段默认拒绝”基线的 5 处局部显式偏离；结构校验通过不等于内容已获准跨边界返回，生产审批仍须单独确认。
- fail-closed：Host/method/path、UUID 路径参数、query string、请求 JSON、字段或请求大小不合规即拒绝；未配置请求 schema 的接口禁止正文。
- 响应边界：通过最大 1 MiB 的内部子请求取得响应；状态码、Content-Type、Content-Encoding、大小、JSON 或响应 schema 未登记即拒绝，原始上游正文不回显。
- 本地审计：蓝/黄分别写 `/data/openresty-waf/audit/access.log`，全量保存原始请求、规范化转发请求、原始上游响应和实际返回响应正文，并保存节点、来源、Host、rule/trace、动作、大小及 SHA-256、响应 schema 和上游状态。当前实现与 `BY-002`“黄区原文写入审计日志”禁止项冲突，属于明确的基线偏离，不代表获准生产放行。
- 一致性：蓝、黄两侧分发同一份活动规则文件。
- 请求边界：为容纳最长 20000 个 UTF-8 字符的 Cypher，请求 JSON 技术上限为 128 KiB；响应技术上限保持 1 MiB。
- 规则体检与测试：`make lint`、`make test`；本地 `make serve && make smoke` 只演示显式加载的知识库示例。

当前主分支未覆盖的控制点：

- 绿->蓝企微 Channel 入站签名和消息 schema。
- 蓝->绿 `114服务器 -> 智伴` 状态 schema。
- 黄->蓝脱敏知识流的文件类型、字段和大小白名单。
- 蓝->黄 Git 单向同步和受控服务的四层白名单。
- `BY-002` 的四层 ACL 记录、来源系统身份、QPS 和责任材料。
- 新增四接口的实际错误状态码、错误响应结构及业务级大小上限尚未登记。
- `POST /ai/knowledge/graph/query` 的只读 Cypher 语义由黄区知识库服务控制，当前 WAF 不解析 Cypher 语法。
- 响应 schema 只能控制已登记结构，不能独立判断 `content`、`metadata` 等字段中的 K3 内容；业务服务仍须承担数据分级和脱敏责任。
- SIEM 审计外发。
- OpenClaw 控制面 `18789` 的四层隔离落地。

## 9. 上线放行门禁

任何跨边界链路进入生产放行前，必须满足：

1. 每条链路必须有方向、源系统、目标系统、协议端口、来源控制、owner 和有效期。
2. 每条链路必须明确允许内容和禁止内容。
3. 黄区出区材料必须完成脱敏和敏感信息扫描。
4. 蓝区回绿区只能传 K0/K1 状态和摘要数据。
5. OpenClaw 控制面 `18789` 不允许进入任何跨区业务白名单。
6. 新增运行配置前必须通过规则检查和测试；蓝、黄两侧必须分发同一份 `conf/waf_rules.lua`。
7. 生产放行前必须有拒绝用例、审计日志查询方式和回滚方式。
8. `BY-002` 必须通过四层拒绝用例证明无法绕过蓝 WAF 或黄 WAF，且黄 WAF 端口不接受未登记来源。
9. 五个接口及逐状态码响应 schema 必须分别验收，包含 Host、method、路径、UUID、字段和状态码拒绝用例；蓝/黄两端应能按同一 trace_id 查询审计记录。
