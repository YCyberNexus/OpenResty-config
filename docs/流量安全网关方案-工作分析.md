## 1. 方案一句话概述

用一台（实为一组 keepalived 主备）VM 作为黄区↔蓝区及对外的**唯一四层（L3/L4）出口**，四层默认 `DROP`、把所有业务流量强制"抬"到本机 OpenResty 七层 WAF；七层做**身份鉴权 + URL 白名单（正则优先、全量兜底，未匹配默认拒绝）+ body 强制 JSON 结构与内容校验**，校验通过后由出口 VM 主动发起一条全新连接（终结-重建）到对端 OpenClaw，全程 fail-closed + 全量审计。**因调用为双向，黄、蓝两侧都需对称地经过该网关并各自过 WAF。**

## 2. 整体架构（流量怎么串起来）

理清四个维度的交集后，**只有一条主数据面路径**，各维度是这条路径上的不同环节，不是并列的多套系统：

```
黄区调用方（本地大模型 / 自建 OpenClaw）            ┌─ 反向：蓝区 OpenClaw 回调黄区，走同一条链路（对称）
        │  ① 路由把"去蓝区/对外"的下一跳收口到出口 VM 的 VIP   │
        ▼                                                   ▲
┌───────────────────────────────────────────────────────────────┐
│  出口 VM（keepalived 主备，持 VIP）                            │
│  【四层 L3-L4】nftables policy DROP                            │
│   ② 仅放行：DNAT 到本机 OpenResty 的业务端口 + 运维口 + VRRP   │
│   ③ forward 链不放行黄↔蓝直接转发（堵死四层直通）             │
│        ▼  DNAT / stream 收口到本机 http listener（TLS 终结）   │
│  【七层 http{} = WAF，access_by_lua 阶段，决策链短路】          │
│   ④ mTLS / API Key 身份鉴权（双向互验）+ 身份→URL/字段最小权限 │
│   ⑤ 先黑名单（注入特征）→ 再 URL 白名单（正则桶 + radix tree） │
│      → body：read_body→cjson.safe→JSON Schema（OpenAI 兼容）   │
│         + messages 专项（role 白名单 / 条数 / 单条+总长）      │
│         + 内容模式匹配（禁代码/注入，纵深防御一层）            │
│   ⑥ 未命中 / 校验失败 → 403/400/413/422，连接就地终止          │
│  【七层主动发起新连接】proxy_pass 到对端 OpenClaw upstream     │
│   ⑦ upstream 叠加 mTLS（对端只信任出口 VM 客户端证书）        │
│  【log_by_lua】结构化 JSON 审计（身份/URL/命中规则/处置/脱敏） │
└───────────────────────────────────────────────────────────────┘
        │  ⑧ 四层 SNAT 保证回程对称回到出口 VM
        ▼
蓝区 OpenClaw（主机防火墙源 IP 白名单：仅放行出口 VM；旁路被双重收口堵死）
```

**维度交集的去重结论（实现时务必遵守）：**

1. **四层 vs 七层职责边界**：四层（nftables + stream）只负责"让流量物理上绕不开、并被抬到七层"，**绝不做任何应用层规则匹配**；所有 URL/body/身份规则都在七层 `access_by_lua`。二者通过"本机 listener 端口 + proxy_protocol 透传的真实源 IP"解耦衔接。
2. **"抬到七层"必须是"终结-重建"**：四层把 TCP 连接 DNAT/proxy_pass 到本机 http server 终结解密，七层校验通过后由出口 VM 主动发起一条全新连接到对端。纯 TLS 透传（`ssl_preread` 不终结）下 WAF 看不到加密内容 = 没校验。**因已确认不要求 E2E，本方案确定走终结-重建。**
3. **body 校验只实现一套**：四层、WAF、body、跨区各维度都提到 body 校验，落地上只实现一条 `access_by_lua` 校验链（读取→解析→JSON Schema→messages 专项→内容匹配→失败响应），由 URL 路由选对应 schema。
4. **审计日志只实现一套 pipeline**：四层 nftables/conntrack 审计 + 七层 `log_by_lua` JSON 审计，统一外发一个 SIEM/ELK，用 trace id 贯穿四层七层关联真实源 IP。
5. **单点出口的 HA/性能/旁路收口只规划一次**：keepalived 主备 + conntrackd 同步 + 容量压测 + 路由/安全组双重收口。
6. **双向对称**：因调用双向，上述链路在黄→蓝、蓝→黄两个方向都要成立。出口 VM 需同时承担两个方向的收口与 WAF；身份鉴权用 mTLS 双向互验最自然；请求体与回调体都要校验。

## 3. OpenClaw（龙虾）接口画像

> 来源：OpenClaw 官方文档与多家 LLM 服务商的 OpenClaw 集成文档（见文末参考）。部分细节官方未完整披露，标注为"推断"，需在 P0 向 OpenClaw 团队最终确认。

- **形态**：自托管网关守护进程（systemd/launchd），把聊天平台（Discord/Slack/Telegram/WhatsApp/iMessage/Signal/Matrix 等）接到 AI 编码 agent / LLM provider。
- **控制面端口**：默认 `127.0.0.1:18789`（HTTP，dashboard/control UI）。`openclaw gateway --port 18789`。**安全要点：控制面绑回环、面向本机管理，绝不应跨区暴露**；跨区只应暴露受控的业务调用端点。
- **对 LLM 后端的调用**：**OpenAI 兼容**。配置 `"api": "openai-completions"`、`baseUrl`（形如 `https://<host>/v1`）、`apiKey`、`models` 数组。即调用标准 `/v1/chat/completions`。
- **请求体结构（OpenAI Chat Completions 兼容）**：顶层 `{ model, messages: [{role, content}], stream?, temperature?, top_p?, max_tokens?, n?, stop?, tools? ... }`；`role ∈ {system, user, assistant, tool}`；`content` 为字符串或多模态数组。→ **WAF 的 body schema 可直接按此建模。**
- **鉴权**：对后端用 `Authorization: Bearer <apiKey>`（provider 级）；渠道侧入站用 pairing 配对码 + `allowFrom`/`dmPolicy` 白名单。**网关层应在此之上叠加自己的身份（mTLS / 网关签发的独立可吊销 key），不要复用 provider key 做跨区鉴权。**
- **流式**：OpenAI 兼容通常支持 `stream: true`（SSE）。**按"可能流式"处理**：请求体仍可一次性校验；流式响应需逐块过滤或按需关 `proxy_buffering`。是否真启用流式待 P0 确认。
- **配置文件**：`~/.openclaw/openclaw.json`（JSON），如 `{"agent":{"model":"<provider>/<model-id>"}}`。
- **远程访问**：官方推荐 Tailscale（HTTPS）。本方案以出口 VM 网关取代/补充该路径，确保所有跨区调用经 WAF。

**对方案的直接影响：**
- body 校验 schema 起步即可用 OpenAI Chat Completions 标准（见 P3-3/P3-5），无需等所有契约就能开工。
- `model` 字段做白名单，匹配后端实际暴露的 model id。
- 控制面（18789）与业务端点要在 WAF 上区分：**跨区只放行业务调用，拒绝一切控制面/管理端点**。
- 双向意味着黄、蓝两侧 OpenClaw 互为 client/server，两端都要部署/经过网关并互验身份。

## 4. 工作分解（按依赖顺序）

> 工作量记号：低 ≈ 1–3 人天，中 ≈ 1–2 人周，高 ≈ 2 人周以上。

### 阶段 P0 — 前置确认与基线（关键路径，可并行启动）

- **P0-1 跨区网络与合规审批前置**（中，依赖网络/安全团队）— ⏸ 对应搁置项 4。确定黄/蓝网段、出口 VM 内外网 IP 与 VIP 规划；确认能否改三层交换/VPC 路由表与安全组；明确审批周期。**双向需确认两个方向的路由牵引与放行。** 产出：网段/IP/VIP 规划表、路由变更清单、审批进度跟踪。
- **P0-2 接口契约与数值上限冻结**（中，依赖应用方 / OpenClaw 团队）— ⏸ 对应搁置项 5。基线已知：OpenAI 兼容 `/v1/chat/completions`。待补：完整 URL 清单、各接口字段精确 schema、是否真流式、body 最大尺寸、messages 最大条数、单条与总长上限、model/参数白名单、双向各端点。产出：链路清单表（source/target/方向/协议/端口）、字段契约、数值上限表。
- **P0-3 环境与技术栈基线（M0）**（低，依赖运维方）— 统一 OpenResty 版本（建议 1.21.4.x 或 1.25.3.x，含 LuaJIT）与部署形态（VM 直装 vs 容器）；搭"mock 上游 OpenClaw + OpenResty 网关 + 请求注入客户端"测试环境；定仓库目录骨架：`nginx.conf` / `conf.d/` / `lua/`（规则模块）/ `rules/`（规则数据）/ `schemas/`。产出：版本/依赖锁定文档、测试环境、仓库骨架。
- **P0-4 第三方依赖与编译方式确认**（低，依赖运维方）— 确认黄/蓝区能否 `opm`/`luarocks` 装 `lua-resty-radixtree`、`lua-resty-jsonschema`，能否带 ModSecurity 重编译。产出：依赖白名单与打包方案。

### 阶段 P1 — 四层骨架（M1）— ⏸ 受搁置项 4 阻塞

- **P1-1 网络拓扑与路由收口**（高，依赖 P0-1）— 把出口 VM（VIP）设为黄↔蓝两个方向的默认网关/下一跳；取消黄蓝子网间直通/对等路由；按业务用策略路由 `ip rule ... lookup waf-table` + fwmark 选路；对外 SNAT/MASQUERADE 保证回程对称；入站 DNAT 映射到 OpenResty 端口；对端 OpenClaw 安全组**只放行出口 VM IP**兜底。验收：两侧 `traceroute` 对端，必经跳为出口 VM；绕过路径无放行规则。产出：策略路由脚本、路由表变更清单、对端源 IP 白名单、旁路封堵 checklist。
- **P1-2 nftables 默认 DROP 最小放行**（中，依赖 P1-1）— `input`/`forward` 链 `policy drop`；`ct state established,related accept`；**forward 链不放行黄↔蓝直接转发**（强制 DNAT 到本机后由七层重建）；`synproxy`/`limit rate` 抗 SYN flood；规则持久化 `/etc/nftables.conf` 原子 reload；`log prefix "L4-DROP "` + ratelimit 记录被拒包。产出：完整规则集、运维/心跳端口白名单 set、L4-DROP 日志规则。
- **P1-3 OpenResty stream 收口与边界**（中，依赖 P1-2 + 七层 listener/证书规划）— `stream{}` 只做端口收口、TLS 终结、`limit_conn`，绝不做规则匹配；非 HTTP 协议默认拒绝；`proxy_pass` 到 `127.0.0.1` 的 http listener；开 `proxy_protocol` 透传真实源 IP。产出：`stream{}` 配置、四层→七层衔接配置、非 HTTP 协议放行/拒绝决策表。

### 阶段 P2 — 七层 WAF 规则引擎（M2）

- **P2-1 WAF 选型与 PoC**（中，依赖 P0-4）— **以自研 `access_by_lua` 轻量引擎为主体**承载白名单与业务规则（最契合 fail-closed 与自定义 schema），可选叠加 OWASP CRS（ModSecurity v3 / Coraza）做通用攻击签名黑名单底座。PoC 跑通"一条白名单 URL + 一个 JSON body schema"端到端，压测 P99 增量 < 1ms。产出：选型对比、PoC 最小 `nginx.conf`、压测基线。
- **P2-2 白/黑名单数据结构与匹配引擎**（高，依赖 P2-1 + P0-2 URL 清单）— 精确/前缀用 `lua-resty-radixtree` 或 Lua hash；正则用 `ngx.re.match` 带 `jo`（JIT + 缓存）。**关键优化**：按 `method+host+路径前缀` 用 radix tree 分桶，桶内只跑少量正则，把候选正则压到个位/十位数。规则统一对象 `{id,type,scope,match,pattern,action,priority}`，所有正则 `init` 阶段预编译缓存。产出：规则对象 schema、URL 匹配器模块、正则预编译/缓存封装。
- **P2-3 优先级与短路决策链（默认拒绝兜底）**（中，依赖 P2-2）— **先黑后白 + 默认拒绝**：① 先过黑名单（命中即 403 短路，避免白名单 URL 上携带攻击 payload 被放行）；② 再过白名单（URL + body 全过才放行）；③ 兜底 `default deny`。scope 短路：URL 不过直接拒绝、不读 body。给运维一个"可信源例外通道"处理黑名单误杀。产出：判定真值表、决策链 Lua 实现、覆盖所有分支的单测（`busted`/`resty`）。

### 阶段 P3 — body 强校验（M3，与 P2 强耦合）

> P3-1~P3-7 共同组成一条 body 校验链，在 `access_by_lua` 中按序执行，由 URL 路由选 schema。OpenClaw 既为 OpenAI 兼容，schema 即按 Chat Completions 建模。

- **P3-1 安全读取 body 并控制大小**（低，依赖 P1-3）— `ngx.req.read_body()` + `get_body_data()`；**把 `client_body_buffer_size` 调到与 `client_max_body_size` 一致**（如 1m/2m），超限直接 413，避免大 body 落盘导致 `get_body_data()` 返回 nil 被误判为空 body 放行；强制 `Content-Type: application/json` 白名单（防 multipart 绕过）；GET/无 body 短路。产出：`read_json_body()` 封装、body 大小配置、Content-Type 校验片段。
- **P3-2 JSON 解析与解析层防护**（低，依赖 P3-1）— `cjson.safe`/`pcall` 包裹 `decode`（异常转 400）；`cjson.decode_max_depth(20)` 防深嵌套 DoS；顶层类型必须是 object。产出：安全解析封装、统一解析失败返回。
- **P3-3 JSON Schema 校验（OpenAI Chat Completions）**（中，依赖 P3-2 + P0-2 + P0-4）— 优先 `lua-resty-jsonschema`（启动时 `compile` 预编译缓存 validator）；按 URL 选 schema；**`additionalProperties:false` 实现严格字段白名单**（收紧 `/v1/chat/completions` 顶层为 `model/messages/stream/temperature/top_p/max_tokens/n/stop/...`）。依赖受限时退化为自研字段校验器。产出：`schemas/chat_completions.json` 等、编译缓存模块、URL→schema 映射。
- **P3-4 字段级约束细化**（中，依赖 P3-3）— 每字段 type + 边界（`maxLength` 注意字节 vs 字符，中文按 `utf8.len` + 字节双重限制）、`enum`（model/role/stream）、`pattern`（id/token 字符集）、数值范围（`temperature`/`top_p`/`max_tokens`）、`required`。产出：字段约束清单、嵌入 schema 的约束、跨字段业务校验。
- **P3-5 大模型 messages 专项限制**（中，依赖 P3-4 + P0-2）— `role` 枚举仅 `system/user/assistant`（按需 `tool`）；限 `system` 消息 0~1 条且必须首位（防伪 system 越权注入）；`maxItems` 限条数；单条 `content` `maxLength` + **自研循环累加校验 messages 总长**（schema 难表达跨元素求和）；`content` 必须为 string 或受控多模态白名单；可选由网关统一注入 system prompt、禁止客户端自带。产出：chat 专用 schema、messages 遍历校验器、model/参数白名单与范围表。
- **P3-6 内容层禁代码/防注入模式匹配（含局限说明）**（高，依赖 P3-5 + 安全团队样本集）— 对 `content` 用 `ngx.re.find` 带 `jo` 匹配 SQL/shell/script/code fence 与 prompt 注入特征（"ignore previous instructions"/"忽略以上指令"/"reveal your system prompt" 等）；规则做成可热更规则表；只对受控文本字段跑、超长截断/抽样。**必须在方案中写清局限**：关键字/正则对 base64/同形字/拆词/语义级注入本质无效，存在漏报误报，绝不能作为唯一防线，需配合字段白名单 + 结构强约束 + 最小权限。产出：危险内容规则表、内容匹配模块、热更新机制、局限性说明段落。
- **P3-7 校验失败响应规范与脱敏审计**（低，依赖 P3-1~P3-6）— 统一错误体 `{code,message,request_id}`，状态码区分 413/400/422/403，对外不回显具体规则与原始内容（防绕过）；`log_by_lua` 记命中规则/字段/处置，**body 内容脱敏/截断/hash**（防审计本身成数据外泄/合规风险）。产出：错误响应函数与状态码映射、审计日志格式与脱敏规则、log-only 灰度开关。

### 阶段 P4 — 跨区身份鉴权与衔接（与 P2/P3 并行；因双向需重点设计）

- **P4-1 四层→七层衔接 + 七层→对端重建**（中，依赖 P1-3 + P2/P3）— 四层把连接交给本机 http server，`access_by_lua` 跑完整决策链；通过后 `proxy_pass` 到对端 OpenClaw upstream（出口 VM 主动发起的全新连接）；upstream 叠加 mTLS（`proxy_ssl_*`），对端只信任出口 VM 客户端证书；失败兜底 deny 时 403/close + 写审计，绝不 fallthrough。产出：衔接配置、proxy_pass + mTLS 配置、职责边界文档。
- **P4-2 双向身份鉴权与最小权限授权**（中，依赖 P0-2 + P1）— **因调用双向，黄、蓝互为 client/server，推荐 mTLS 双向互验**（跨区更稳妥），每条链路/调用方签发独立可吊销凭证；`access_by_lua` 校验证书指纹/Key，再查"身份→可访问 location/URL→可用字段"授权表（`lua_shared_dict` 或本地 JSON 加载，不每请求外呼）实现最小权限；凭证与上游真实地址解耦；**两个方向各自一套授权表**；鉴权失败落审计。产出：身份签发/吊销方案、鉴权 Lua 脚本、双向身份→URL/字段授权表。
- **P4-3 流式/协议适配**（中，依赖 P0-2 确认是否流式）— 默认 HTTP/REST + JSON（OpenAI 兼容）。若启用流式 SSE/chunked：只校验请求体 + 逐块过滤响应 + 按需关 `proxy_buffering`；响应方向（含双向回调体）也要校验。产出：协议确认结论、流式/非流式两套代理与校验策略。

### 阶段 P5 — 规则配置化、热更新与可维护性（与 P2/P3 并行）

- **P5-1 规则配置化与热更新**（高，依赖 P0-4）— 规则源用 JSON/YAML（可读、可 diff、可入库）；热更用"**`lua_shared_dict` 存版本号 + 原始规则文本，各 worker 本地 `lua-resty-lrucache` 缓存编译后正则句柄**"模式（正则对象不能直接放 shared dict）；`ngx.timer.every` 拉版本号变化重编译；**加载前强制配置校验**（JSON 合法性 + 正则可编译 + schema 完整），失败保留旧版本并告警，**绝不让坏配置导致 fail-closed 全站 403**；一键回滚到上一版本号。产出：规则配置格式规范、热更新加载器、配置校验器与坏配置兜底、版本号与回滚。
- **P5-2 规则可维护性与版本管理**（中，依赖 P5-1）— 规则入 Git（即本仓库），目录按 scope 拆 `rules/url/whitelist.json`、`rules/body/<service>.schema.json`、`rules/exceptions/<app>.json`（运维为不规范应用单独配的例外，隔离避免污染主白名单、便于后续推动整改下线）；每条规则带元数据（owner/创建时间/工单/环境）；变更流程：应用方提清单→运维方转写 + code review→CI 跑配置校验 + 单测→灰度。产出：目录与命名规范、元数据字段定义、变更/评审流程、CI 配置校验流水线。
- **P5-3 性能优化（正则/JIT/缓存/ReDoS）**（中，依赖 P2-2 + P3）— 正则带 `jo`，`lua_regex_cache_max_entries` 足够大常驻；`lua_regex_match_limit` 防 ReDoS；radix tree 分桶压候选集；body 只在 URL 通过后读、设大小上限；`lua-resty-lrucache` 缓存幂等 URL 判定；access 阶段不做阻塞 IO；`wrk2` 压测设性能预算（如 P99 增量 < 2ms），观测 LuaJIT GC、火焰图。产出：性能预算与压测报告、ReDoS 防护配置、分桶+缓存实现、GC/内存基线。

### 阶段 P6 — 高可用、性能容量与审计 — ⏸ 容量定型受搁置项 6 影响

- **P6-1 出口 VM 高可用**（高，依赖 P1 + 第二台同规格 VM）— `keepalived`（VRRP，云不支持组播时走单播 + HAVIP/弹性网卡漂移 API）一主一备，路由/默认网关/DNAT 目标全指向 **VIP**；`vrrp_script` 健康检查（进程、监听端口、到对端探活）；nftables/OpenResty/策略路由两台用 ansible/git 同步；**`conntrackd` 同步连接状态**（避免切换时长连接/流式问答被重置）；心跳走独立网段并在 nftables 放行防脑裂；切换/回切演练。产出：keepalived 主备配置 + 健康检查、conntrackd 配置、切换演练手册与告警接入。
- **P6-2 出口 VM 性能瓶颈评估与调优**（中，依赖 P0-2 峰值目标 + P6-1）— 连接/句柄（`worker_connections`、`worker_rlimit_nofile`、`somaxconn`、`ip_local_port_range` 防 SNAT 端口耗尽）；`nf_conntrack_max` 调大并监控，纯转发可 `notrack`；网卡 RSS 多队列 + RPS/XPS + irqbalance 防单核 softirq 跑满；TLS 终结开 `ssl_session_cache`、OCSP stapling、`worker_cpu_affinity` 绑核、考虑 AES-NI；`wrk2`/`tcpkali` 压测，`sar`/`ss`/`nstat`/`perf` 观测；给出扩容阈值与横向扩展预案。产出：容量压测报告、调优基线、扩容阈值与预案。
- **P6-3 出口流量审计与日志**（中，依赖 SIEM/ELK + proxy_protocol）— 四层 nftables `nflog`/`ulogd2` 记 DROP/放行元数据（限速）+ `conntrackd`/`conntrack -E` 记会话；七层 `log_format` JSON + `log_by_lua` 记 `remote_addr`（proxy_protocol 真实源）、host、uri、method、status、命中规则 ID/动作、body 校验结果；统一外发 SIEM/ELK（`rsyslog`/`filebeat`/`vector`，**禁止只落本地**）；关键事件实时告警；满足留存周期 + 防篡改（WORM/只读归档）；trace id 贯穿四层七层。产出：四层审计配置、七层 JSON 日志 + 命中写入、外发 pipeline 与告警、留存防篡改方案。

### 阶段 P7 — 联调、上线与运营（M4 + 灰度）

## 6. 风险清单

**A. 单点出口（可用性 + 瓶颈）**
1. 出口 VM 是单点故障也是单点瓶颈：宕机即跨区/对外全断，过载即全链路降速。即便 keepalived 主备，单 VM 的带宽/PPS/`nf_conntrack_max`/SNAT 本地端口仍是硬上限。
2. 主备切换若未 `conntrackd` 同步，长连接（流式问答）会被重置。
3. 默认 DROP 把自己锁死：漏放 SSH/VRRP 心跳/健康检查会致运维失联或脑裂；变更需带带外通道与自动回滚。

**B. 旁路与路由（双向放大暴露面）**
4. 旁路未封死：主机内 DROP 了但网络侧仍有黄↔蓝直连路由/对等连接，攻击者可绕过七层；必须路由表 + 对端主机防火墙/安全组**双重收口**。
5. 非对称路由：只改去程没做 SNAT，回包不经出口 VM 被 conntrack 丢弃；去回程都必须经出口 VM。
6. 误把四层当七层用 / 纯 TLS 透传：四层看不到应用层；跨区流量必须在出口 VM 终结再重建（已确认不要求 E2E，可终结）。
7. **双向暴露面翻倍**：反向链路（蓝→黄）同样是攻击面，必须同等强度过 WAF + 鉴权，不能只防一个方向。

**C. WAF 逻辑与配置（fail-closed 双刃剑）**
8. 白名单 fail-closed：规则加载失败/正则编译错误可能致全站 403；必须"坏配置不生效、保留旧版本、不降级为全拒"，加载前强制校验。
9. 黑白名单优先级设反留逻辑漏洞：推荐先黑后白，给黑名单误杀一个可信源例外通道。
10. 应用方 URL 不规范致 `exceptions` 规则膨胀难维护，掩盖应用方整改责任；白名单完整性与长期维护成本是最大隐性风险。

**D. body 校验**
11. 大 body 落盘陷阱：超 `client_body_buffer_size` 时 `get_body_data()` 返回 nil，未处理会把超限请求误判为空 body 放行；把 buffer_size 调到与 max_body_size 一致。
12. Content-Type 绕过：不强制 `application/json` 可用 text/plain/multipart 夹带绕过。
13. `additionalProperties` 未设 false 时未知字段可夹带绕过；role/system 越权：仅枚举 role 不够，未限 system 数量与位置时客户端可自带伪 system 注入越权指令，内部互通风险更高。
14. 长度计量歧义：`maxLength` 按字节还是字符，中文/emoji 差异大；单条限了总长未限会打穿上下文/成本，需双重限制并明确口径。
15. cjson 深度/异常：未设 `decode_max_depth`、未 `pcall` 包裹，深嵌套或非法 JSON 触发 DoS/500。

**E. 内容匹配的根本局限**
16. "禁止代码"易误判：大模型问答天然含代码片段，正则黑名单要么过严误杀、要么被编码/拆词绕过；模式匹配对语义级 prompt 注入本质无效，**绝不能作为唯一防线**。

**F. 性能**
17. 正则规模增长引发退化与 ReDoS：必须 `jo` + `lua_regex_match_limit` + radix tree 分桶；schema 每请求重复编译会显著掉性能，必须预编译缓存；正则无法直接放 shared dict 导致 worker 间不一致。

**G. 审计与合规**
18. 日志只落本地：出口 VM 沦陷时本地日志可被篡改，必须实时外发独立 SIEM + 防篡改归档。
19. 真实源 IP 丢失：四层终结重建后到对端源 IP 变成出口 VM，未配 proxy_protocol/XFF 则无法追溯定责。
20. 审计记问答原文会成跨区数据外泄/合规风险点，需脱敏/截断/hash。

**H. 流程与未知**
21. 跨区网络可达性与合规审批不可控，往往是项目关键路径瓶颈（搁置项 4）。
22. 契约数值上限未定（搁置项 5）：schema 字段形态已知（OpenAI 兼容），但条数/长度/参数范围待补，否则 messages 专项限制无法定数。
23. 容量与 HA 形态未定（搁置项 6）：影响是否前置 LVS 及"唯一出口"约束的重新界定。
24. ModSecurity/CRS 偏黑名单异常打分，强行作主体承载白名单默认拒绝会与业务约束不匹配；建议只做黑名单底座。
25. OpenClaw 控制面（18789）若被跨区可达，等于绕过业务 WAF 暴露管理面；必须确保跨区只暴露受控业务端点。

10. **【规则规模与载体】** 规则总量级（决定是否必须 radix tree 分桶）？配置源选文件/配置中心（Apollo/Nacos/etcd）/DB？黄/蓝区是否允许 OpenResty 出站访问配置中心？（运维方）
11. **【内容校验边界】** "禁止代码/越权指令"具体禁什么（防注入？防外泄？正常代码问答是否也禁）？判定标准（正则/关键字/语义）？是否要求网关统一注入/接管 system prompt、禁止客户端自带？是否需请求+响应（含回调）双向校验？（应用方/业务/安全）
12. **【白名单责任与 SLA】** 应用方能否提供完整规范 URL 清单？URL 不规范时运维方单独配规则的工作量与 SLA？误杀申诉时效？观察模式需跑多久才切强制拦截？（应用方/运维方）
13. **【凭证管理】** 双向 mTLS 证书/API Key 由谁签发、轮换、吊销？最小权限授权粒度到 URL 还是字段？（运维/应用方）
14. **【可观测与合规】** 现有是否有 Prometheus/Grafana/ELK/SIEM 可复用？日志脱敏与留存要求（能否记问答片段、保留多久、是否需 hash）？等保/审计合规？规则变更评审 RACI？（运维/安全/合规方）
15. **【OpenClaw 控制面】** 跨区是否会暴露 OpenClaw 控制面（默认 `127.0.0.1:18789`）？确认跨区只暴露业务调用端点、拒绝管理面。（运维/安全 + OpenClaw 团队）
