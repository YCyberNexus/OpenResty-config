# 绿蓝黄数据链路与白名单管控设计

日期：2026-07-06

## 1. 背景与目标

领导要求对齐 `绿<=>蓝`、`蓝<=>黄` 全线路，并梳理清楚数据链路白名单。核心安全口径是：任何经过安全边界的数据都必须被管控，尤其是后续的知识流动。

本设计把现有 `OpenResty-config` 仓库中的七层 WAF 能力，与 Claude Code 项目记忆中的三色分区、OpenClaw 跨区协同架构对齐，形成一份可落地的链路台账和控制矩阵。

## 2. 信息来源

- 当前仓库：`README.md`、`conf/nginx.conf`、`conf/waf_rules.lua`、`docs/流量安全网关方案-工作分析.md`、`docs/WAF规则配置指南.md`、`docs/WAF运维交接说明.md`。
- Claude Code 项目记忆：
  - `company-security-zones.md`：公司三色安全分区定义。
  - `traffic-security-gateway-project.md`：OpenResty 网关项目背景、六条跨区边界、OpenClaw 跨区互联方案。
- 用户补充：黄区代码、数据、文档脱敏后可通过 OpenClaw-to-OpenClaw 通信传给蓝区；蓝区任务状态可通过 `114服务器 -> 智伴` 链路回传绿区。

## 3. 三色分区定义

公司服务器按安全等级分为三个区：

| 分区 | 定义 | 安全口径 |
|---|---|---|
| 黄区 | 完全的环境隔离，只可以开放某些通道连接其他区 | 最严，默认不通，按通道逐条放行 |
| 蓝区 | 在黄区安全策略之上，额外增加大模型访问能力 | 受控隔离区，承载 OpenClaw、大模型访问和跨区协同能力 |
| 绿区 | 完全的互联网访问，只有少数内容无法访问 | 最开放，外部输入多，需要对进入蓝区和回传数据做边界控制 |

隔离强度为：黄区 > 蓝区 > 绿区。

## 4. 总体架构口径

设计按 `绿区 ↔ 蓝区 ↔ 黄区` 建模，但白名单不能只按双向箭头汇总，必须拆成具体方向和数据类型。

```text
绿区：互联网访问区
  ↕
边界一：绿/蓝
  ↕
蓝区：隔离策略 + 大模型访问能力，OpenClaw hub 所在区
  ↕
边界二：蓝/黄
  ↕
黄区：完全隔离区，代码/数据/文档源头所在区之一
```

关键原则：

1. 所有跨边界链路默认拒绝，只有登记到白名单的源、目标、协议、接口、身份、数据类型可以放行。
2. 黄区出区数据必须先脱敏，再进入允许的通信链路。
3. 蓝区回绿区只允许状态类和必要摘要类数据，禁止把黄区原始代码、数据、文档全文回传绿区。
4. OpenClaw 控制面 `18789` 不进入业务白名单，跨区默认禁止，由四层防火墙和主机绑定策略管控。
5. 当前仓库的 WAF 能力主要覆盖 OpenAI 兼容接口的七层请求侧控制，不能替代四层路由收口、mTLS 身份、响应侧过滤和审计外发。

## 5. 需要登记的边界

Claude Code 项目记忆里已有架构图适配性分析，揭示六条跨区边界。本设计按以下边界建台账：

| 编号 | 边界 | 方向 | 典型链路 | 当前结论 |
|---|---|---|---|---|
| B1 | 绿/黄 | 绿 -> 黄 | 企微 Channel，知识查询 | 特殊跨级链路，必须单独审批，不可被绿/蓝或蓝/黄白名单隐含覆盖 |
| B2 | 绿/蓝 | 绿 -> 蓝 | 企微 Channel，需求研发 | 需要入口签名、消息类型、附件类型和任务字段白名单 |
| B3 | 蓝/黄 | 蓝 -> 黄 | Git 单向同步、任务下发、受控服务访问 | 默认禁止，按通道和目标服务逐条放行 |
| B4 | 蓝/大模型 | 蓝 -> LLM/OpenClaw 业务接口 | OpenAI `/v1/chat/completions` | 当前仓库已覆盖 URL、请求头、`model`、`messages` 的部分七层控制 |
| B5 | 黄/蓝 | 黄 -> 蓝、蓝 -> 黄 | OpenClaw-to-OpenClaw、响应、回调 | 必须补方向、身份、脱敏、响应/回调和知识流动控制 |
| B6 | OpenClaw 控制面 | 管理流量 | `127.0.0.1:18789` | 不允许跨区暴露，不依赖七层 path 黑名单 |

用户补充的 `黄区 -> 蓝区` 脱敏知识流、`蓝区 -> 绿区` 状态回传流，分别纳入 B5 和 B2 的反向受控数据流管理。

## 6. 白名单台账字段

每条白名单必须记录以下字段。没有完整登记的链路不应上线放行。

| 字段 | 说明 |
|---|---|
| 白名单 ID | 稳定编号，例如 `GB-001`、`BY-003`、`YB-KNOW-001` |
| 方向 | `绿->蓝`、`蓝->绿`、`蓝->黄`、`黄->蓝`、`绿->黄` |
| 边界 | `绿/蓝`、`蓝/黄`、`绿/黄`、`控制面` |
| 源分区和源系统 | 绿区企微 Channel、蓝区 OpenClaw hub、黄区 OpenClaw node、114 服务器等 |
| 目标分区和目标系统 | 蓝区 hub、黄区 node、智伴、Git 服务、模型服务等 |
| 协议端口 | HTTP、HTTPS、WSS、Git、企微回调等 |
| 身份凭证 | mTLS 证书 CN、API Key、企微签名、服务账号、Token |
| 接口白名单 | host、path、method、callback 路径、Git remote、WSS path |
| 数据白名单 | 允许传输的字段、消息类型、文件类型、内容类别 |
| 禁止项 | 不允许出现的字段、头、文件、原文材料、控制面地址 |
| 脱敏要求 | 黄区出区前的脱敏规则、敏感信息扫描、人工/自动审批 |
| 大小和频率限制 | 单条消息大小、附件大小、批量条数、QPS、回调频率 |
| 审计字段 | request_id、task_id、source identity、rule_id、数据摘要 hash、处置结果 |
| 责任归属 | 业务 owner、运维 owner、安全审批人、工单号、有效期、复核周期 |
| 验证方式 | 冒烟命令、日志查询、拒绝用例、旁路验证、回滚方式 |

## 7. 边界管控矩阵

| 链路 | 数据流 | 允许内容 | 禁止内容 | 控制点 |
|---|---|---|---|---|
| 绿 -> 蓝 | 需求、任务、企微消息、用户输入 | 已登记消息类型、任务字段、必要附件元数据 | 未登记附件、可执行载荷、未审计外部内容、伪造回调 | 企微签名、来源身份、URL/method 白名单、内容类型白名单、审计 |
| 蓝 -> 绿 | 任务状态经 `114服务器 -> 智伴` 回传 | 任务 ID、阶段、成功/失败、错误码、必要摘要、时间戳 | 黄区原始代码、原始数据、文档全文、模型完整推理上下文 | 状态字段 schema、长度限制、敏感信息扫描、审计 hash |
| 蓝 -> 黄 | Git 单向同步、任务下发、黄区受控服务访问 | 已登记 repo、branch、任务指令、协议端口 | 任意服务探测、横向访问、未审批端口、控制面访问 | 四层路由收口、mTLS、Git/service 白名单、最小权限账号 |
| 黄 -> 蓝 | 脱敏后代码、数据、文档，经 OpenClaw-to-OpenClaw 到蓝区 | 脱敏片段、摘要、结构化元数据、允许的文件类型 | 黄区原始资料、密钥、凭证、个人信息、内部地址、未脱敏日志 | 出区前脱敏、DLP/正则扫描、WSS+mTLS、文件类型和大小限制 |
| 蓝 -> 大模型 | OpenAI 兼容请求 | 已登记 URL、`model`、`messages`、允许字段 | `x-openclaw-*` 覆盖头、未登记 model、tools/function 调用、未知字段 | 当前 `conf/waf_rules.lua` + 请求体校验 + 禁用头 |
| 大模型 -> 蓝 | 模型响应、流式块、工具结果 | 响应状态、受控答案、允许的结构化结果 | 反向注入、越权系统提示、敏感原文回显 | 响应/SSE 过滤、日志脱敏、超长截断 |
| 控制面 | OpenClaw `18789` | 本机回环管理 | 跨区访问 | 主机绑定 `127.0.0.1`、四层防火墙、不进业务 WAF 白名单 |

## 8. 知识流动管控

本项目中的“知识流动”包括但不限于：

- 黄区代码片段、配置片段、日志片段。
- 黄区业务数据、测试数据、数据库导出、问题样本。
- 黄区文档、接口说明、设计说明、运维手册。
- 进入模型的 prompt、system message、RAG 检索内容。
- 模型响应、工具调用结果、任务执行状态。
- 审计日志中的摘要、命中规则、错误信息。

知识流动控制按四级处理：

| 级别 | 说明 | 跨边界策略 |
|---|---|---|
| K0 | 无敏感信息的状态数据 | 可蓝->绿回传，但必须字段白名单化 |
| K1 | 低敏摘要、任务进度、错误码 | 可跨边界传输，限制长度并记录 task_id |
| K2 | 脱敏后的代码、数据、文档片段 | 仅黄->蓝允许，必须脱敏、扫描、记录 hash |
| K3 | 原始代码、原始数据、密钥、凭证、未脱敏文档 | 禁止出黄区，禁止回传绿区 |

黄区出区的 K2 数据必须满足：

1. 已关联具体任务或工单。
2. 已完成脱敏，删除密钥、Token、内网地址、账号、个人信息和未授权业务数据。
3. 文件类型和大小在白名单内。
4. 通过 OpenClaw-to-OpenClaw 的登记链路传输。
5. 传输前后都记录摘要 hash、任务 ID、源身份、目标身份和时间戳。

蓝区回绿区的状态链路必须满足：

1. 只承载 K0/K1。
2. 走 `114服务器 -> 智伴` 的登记链路。
3. 返回字段必须符合状态 schema。
4. 错误信息只能返回摘要级错误码和必要说明，不回显黄区原始资料。
5. 日志保留可追溯 request_id/task_id。

## 9. 现有仓库能力映射

当前主分支已具备的能力：

- `conf/waf_rules.lua`：最小 URL 白名单，当前放行 `POST /v1/chat/completions` 和 `GET /v1/models`。
- 默认拒绝：未命中白名单返回 `not_in_whitelist`。
- 黑名单优先：`^/admin`、`^/v1/admin` 作七层纵深防御。
- 禁用请求头：`x-openclaw-*` 整族拦截，防止客户端绕过 `model` 白名单。
- `chat` body 校验：字段白名单、`model` 白名单、`messages` 数量和长度限制、`role` 白名单、`system` 必须首位。
- `scripts/check_rules.lua`、`make lint`、`make test`：规则体检和单测。

当前主分支未覆盖或不足的能力：

- 绿->蓝企微 Channel 的入站签名和消息 schema。
- 蓝->绿 `114服务器 -> 智伴` 状态回传 schema。
- 黄->蓝 OpenClaw-to-OpenClaw 的脱敏知识流字段和文件白名单。
- 蓝->黄 Git 单向同步和其他受控服务的四层白名单。
- mTLS 身份、方向维度、证书吊销和最小权限授权。
- 响应/SSE 方向过滤。
- 审计日志外发 SIEM。
- OpenClaw 控制面 `18789` 的四层隔离落地。

Claude Code 项目记忆提到部分能力曾在 `openclaw-muilt` 分支或历史工作中设计/落地，例如 per-profile 框架、企微回调、内容层防注入、跨区 OpenClaw 互联 runbook。当前工作应先核对这些内容是否已合并到当前分支，再决定是补文档、移植配置，还是重新实现。

## 10. 实施顺序建议

优先级按“先封边界，再放业务，再管知识回流”排序：

1. 固化台账：把六条边界、四个方向和白名单字段形成正式台账模板。
2. 补链路清单：让业务/运维补齐源 IP、目标 IP、端口、证书、Token、owner、工单和有效期。
3. 绿->蓝入口：确认企微 Channel、需求研发入口、消息类型和附件策略。
4. 黄->蓝知识流：确认脱敏规则、文件类型、字段白名单、OpenClaw-to-OpenClaw 链路身份。
5. 蓝->绿状态流：确认 114 服务器部署位置、智伴接口、状态 schema。
6. 蓝->黄通道：确认 Git 单向同步、任务下发和受控服务清单。
7. 大模型请求侧：继续收紧当前 `conf/waf_rules.lua` 的 `model`、字段和长度上限。
8. 响应和审计：补响应/SSE 过滤、日志脱敏、SIEM 外发和告警。

## 11. 验收标准

本方案完成后，应能回答以下问题：

1. 每条跨边界链路的方向、源、目标、协议、身份和 owner 是否清楚。
2. 每条链路允许传什么数据、禁止传什么数据是否清楚。
3. 黄区数据出区前的脱敏、扫描和审计是否清楚。
4. 蓝区回绿区是否只传状态和摘要，不传黄区原文。
5. 现有 OpenResty WAF 覆盖了哪些控制点，缺口在哪里。
6. OpenClaw 控制面是否明确不跨区暴露。
7. 新增白名单是否有工单、有效期、复核周期和回滚方式。

## 12. 不在本设计中直接修改的内容

本设计先不直接修改生产运行配置，原因是缺少真实链路材料。以下内容需要在实施阶段按台账材料落地：

- 真实 IP、网段、端口、域名和证书路径。
- 114 服务器所在分区、访问协议、智伴接口契约。
- 黄区脱敏规则的企业级标准和扫描工具。
- 企微 Channel 的 Token、回调路径、消息加解密策略。
- Git 单向同步的 repo、branch、账号权限和审计方式。
- OpenClaw-to-OpenClaw 的 WSS path、证书 CN、node 身份和吊销策略。

## 13. 设计结论

领导要求的关键点不是简单补几个 URL 白名单，而是把所有跨边界数据流拆成可审计、可审批、可验证的台账。尤其是后续知识流动，必须从“网络连通”提升到“数据内容可出区、可回传、可追溯”的粒度。

最终落地口径：

- 绿/蓝、蓝/黄、绿/黄特殊链路都要建白名单。
- 请求流、响应流、知识流、状态流都要分别建白名单。
- 黄区原始知识禁止直接出区；脱敏后只允许走登记链路。
- 蓝区回绿区只允许状态和摘要，不允许回传黄区原文。
- 当前仓库 WAF 是七层请求侧控制基础，需要与四层收口、身份、响应过滤和审计外发配套。
