# BY-002 知识库五接口：通用 WAF V2 运维上线说明

## 1. 本次运维要做什么

本次不是只增加五条 URL，而是把蓝、黄 WAF 从 V1 整体升级为通用 V2。两台节点使用同一部署包，
先黄后蓝。包内的现场 IP、端口、Host 和五条知识库规则已经配置完成；运维不需要手改包内文件。

V2 上线后，普通新接口只需替换配置文件并 reload，不再整体部署运行包。

## 2. 部署包

```text
openresty-waf-v2-20260804.tgz
```

交付时同时提供 SHA-256。运维收到包后必须核对：

```bash
sha256sum openresty-waf-v2-20260804.tgz
tar -tzf openresty-waf-v2-20260804.tgz
```

解压后顶层目录必须是 `openresty-waf/`，并同时包含：

- `conf/nginx-blue.conf`、`conf/nginx-yellow.conf`；
- `conf/waf_rules.lua`、`conf/waf_routes.lua`、`conf/waf_policies.lua`；
- `conf/waf-internal-locations.conf` 和其它公共 Nginx include；
- `lua/waf/` 全部 V2 模块；
- `scripts/check_rules.lua`、`scripts/server-setup.sh`；
- 运维文档和 systemd service。

不能把本包中的单个 Lua 文件复制进 V1 目录混用。

## 3. 包内已配置的现场值

| 节点/方向 | 已配置值 |
|---|---|
| 蓝 WAF 监听 | `10.64.5.4:80` |
| 蓝 WAF 下一跳 | `10.64.9.2:80` |
| 黄 WAF 监听 | `10.64.9.2:80` |
| 黄 WAF 下一跳 | `192.168.14.249:6789` |
| 活动 Host | `kb.pxsemic.tech` |
| 入口别名 | `kb-1.pxsemic.tech` 已登记固定路由，但没有接口白名单，继续拒绝 |
| 节点间协议 | HTTP；来源和目标限制由现有四层 ACL 保证 |

`waf_routes.lua` 同时保存 blue 和 yellow 两个角色的固定下一跳。Nginx 不再按 Host 写多个静态
`server`/`upstream`，而是先进入 Lua 精确 Host 白名单，再从固定路由表取下一跳。客户端不能指定
目标 IP、端口或代理 URL。

## 4. 当前放行的五个接口

```text
POST /ai/knowledge/search
GET  /ai/knowledge/assets/{asset_id}
GET  /ai/knowledge/health
POST /ai/knowledge/graph/query
GET  /ai/knowledge/graph/health
```

约束：

- `asset_id` 必须是规范 UUID；
- 五条规则均为 `buffered`，响应完整校验通过前不会返回正文；
- `/search` 只接受文档中的 `query`、`top_k`；
- `/graph/query` 校验 JSON schema，并启用 `cypher_read_only_v1`；写入/管理关键字、`CALL`、分号
  多语句和无法安全解析的语句会拒绝；
- 当前五个接口不接受 Query string 或客户端业务认证头；调用来源身份仍依赖现有四层 ACL；
- `search` 允许文档已知的 200/422/502/503；其它四个接口因源文档没有错误响应结构，当前仅允许
  200。后端返回未登记状态时 WAF 返回 502，不泄露原始正文。

## 5. 预检查

上线前确认：

1. 蓝区调用方到 `10.64.5.4:80`、蓝到 `10.64.9.2:80`、黄到
   `192.168.14.249:6789` 的 ACL 已审批；
2. 后端 `192.168.14.249:6789` 健康，且不能被调用方绕过 WAF 直连；
3. DNS/调用端将 `kb.pxsemic.tech` 指向蓝 WAF；
4. `/data/openresty`、`/opt/openresty-waf`、systemd 权限和审计目录符合现场标准；
5. 日志转储虚拟机已接收 `/data/openresty-waf/audit/access.log`；
6. 已保留完整 V1 包/目录和配置，具备黄先蓝后的回滚窗口。

## 6. V2 首次升级步骤

### 6.1 黄 WAF

将完整目录部署到 `/opt/openresty-waf` 后执行：

```bash
cd /opt/openresty-waf

/data/openresty/luajit/bin/luajit scripts/check_rules.lua \
  conf/waf_rules.lua conf/waf_routes.lua conf/waf_policies.lua

/data/openresty/bin/openresty -p /opt/openresty-waf/ \
  -c conf/nginx-yellow.conf -t

systemctl restart openresty-waf@yellow
systemctl status openresty-waf@yellow --no-pager
```

预期规则检查：`0 error, 5 warning`，并列出五条 BY-002 规则。5 个 warning 只能来自已确认的
metadata、parameters 和 graph rows 动态对象。

在升级蓝 WAF 前，从黄 WAF 本机或批准的蓝 WAF 来源做后端连通和拒绝用例检查，确认黄端审计
正常写入。

### 6.2 蓝 WAF

黄端通过后再执行：

```bash
cd /opt/openresty-waf

/data/openresty/luajit/bin/luajit scripts/check_rules.lua \
  conf/waf_rules.lua conf/waf_routes.lua conf/waf_policies.lua

/data/openresty/bin/openresty -p /opt/openresty-waf/ \
  -c conf/nginx-blue.conf -t

systemctl restart openresty-waf@blue
systemctl status openresty-waf@blue --no-pager
```

## 7. 业务验收

正向用例至少包含：

```bash
curl -sS -H 'Host: kb.pxsemic.tech' \
  http://10.64.5.4/ai/knowledge/health

curl -sS -H 'Host: kb.pxsemic.tech' \
  -H 'Content-Type: application/json' \
  -d '{"query":"ASML 通信异常怎么排查","top_k":5}' \
  http://10.64.5.4/ai/knowledge/search

curl -sS -H 'Host: kb.pxsemic.tech' \
  -H 'Content-Type: application/json' \
  -d '{"cypher":"MATCH (e) RETURN e LIMIT 10","parameters":{},"limit":10}' \
  http://10.64.5.4/ai/knowledge/graph/query
```

拒绝用例至少包含：

| 用例 | 预期 |
|---|---|
| Host 改为 `kb-1.pxsemic.tech` | 403 `not_in_whitelist` |
| 未登记 URL/method | 403 `not_in_whitelist` |
| 资产 ID 非 UUID或多一层路径 | 403 |
| 任一接口增加 Query | 403 `query_not_allowed` |
| JSON 缺必填字段、类型错误、未知字段 | 400/422 |
| 图谱语句包含 `DELETE`、`SET`、`CALL` 或分号 | 422 `request_policy` |
| 错误 Content-Type、压缩响应、未登记状态/schema | 415 或 502 |
| 直接访问 `192.168.14.249:6789` | 四层拒绝 |

在蓝、黄两端分别按响应 `X-Request-ID` 查询同一 trace：

```bash
grep 'TRACE_ID' /data/openresty-waf/audit/access.log
```

应看到相同 rule_id、规范化请求、固定下一跳、上游状态和请求/响应 SHA-256。

## 8. 后续新增接口时运维替换什么

### 8.1 同 Host、同后端的普通接口

只替换：

```text
conf/waf_rules.lua
```

### 8.2 新 Host 或新后端 IP/端口

替换：

```text
conf/waf_rules.lua
conf/waf_routes.lua
```

同时补齐两侧 ACL、DNS/调用配置和审批台账。Nginx 文件不需要因新增 Host 修改。

### 8.3 新的可复用认证/策略实例

再替换：

```text
conf/waf_policies.lua
```

三份配置无论改了几份，都必须一起执行 `check_rules.lua`；然后黄先蓝后执行
`openresty -t` 和：

```bash
systemctl reload openresty-waf@yellow
systemctl reload openresty-waf@blue
```

普通新增接口不替换 `lua/waf/`、`nginx-blue.conf`、`nginx-yellow.conf`，也不重新部署完整包。

## 9. 回滚

首次 V2 升级失败：恢复完整 V1 目录和服务配置，先黄后蓝 restart。不能把 V1 规则与 V2 运行时
混搭。

后续纯配置失败：恢复上一批准版本的 `waf_rules.lua`、`waf_routes.lua`、`waf_policies.lua`，三份
一起体检，先黄后蓝 reload。

回滚后重复健康检查、拒绝用例、直连拒绝和 trace 审计检查。
