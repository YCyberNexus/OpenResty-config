# BY-002 知识库五接口运维配置说明

## 1. 变更目标

将原来直连黄区知识库的五个 API 请求：

```text
http://192.168.14.249:6789/ai/knowledge/search
```

改为经过双 WAF：

```text
调用方
  -> 10.64.5.4:80 蓝 WAF
  -> 10.64.9.2:80 黄 WAF
  -> 192.168.14.249:6789 知识库服务
```

固定 Nginx 中存在两个 Host：

```text
kb.pxsemic.tech
kb-1.pxsemic.tech
```

两个入口当前都指向同一个黄区后端，但活动规则只放行 `kb.pxsemic.tech`；
`kb-1.pxsemic.tech` 不进入七层白名单。黄 WAF 发给后端的 HTTP Host 固定为
`kb.pxsemic.tech`。

本次放行：

```text
POST /ai/knowledge/search
GET  /ai/knowledge/assets/{uuid}
GET  /ai/knowledge/health
POST /ai/knowledge/graph/query
GET  /ai/knowledge/graph/health
```

资产接口的 `{uuid}` 只匹配一个规范 UUID 路径段。不要放行后端 IP 直连、其它 URL、
其它方法、非 UUID 资产路径或 query string。

## 2. 需要部署的文件

部署包内已经包含完整配置，不要在服务器上重新从 `.template` 复制或手填占位符。

| 节点 | 部署文件 | 服务器生效路径 |
|---|---|---|
| 蓝 WAF | `conf/nginx-blue.conf` | `/opt/openresty-waf/conf/nginx-blue.conf` |
| 黄 WAF | `conf/nginx-yellow.conf` | `/opt/openresty-waf/conf/nginx-yellow.conf` |
| 蓝、黄都要相同 | `conf/waf_rules.lua` | `/opt/openresty-waf/conf/waf_rules.lua` |

蓝、黄节点必须使用同一个部署包。两端 `waf_rules.lua` 必须逐字节相同。

通用模板 `nginx-blue.conf.template`、`nginx-yellow.conf.template` 只用于以后经审批迁移
地址，本次部署不要使用。

## 3. 蓝 WAF 配置

文件：

```text
/opt/openresty-waf/conf/nginx-blue.conf
```

必须确认以下内容：

```nginx
upstream yellow_waf {
  server 10.64.9.2:80;
  keepalive 32;
}
```

默认虚拟主机：

```nginx
listen 10.64.5.4:80 default_server;
server_name "";
```

业务虚拟主机：

```nginx
listen 10.64.5.4:80;
server_name kb.pxsemic.tech kb-1.pxsemic.tech;
```

转发黄 WAF 时必须保留原始业务 Host：

```nginx
location ^~ /__waf_upstream/ {
  internal;
  rewrite ^/__waf_upstream(/.*)$ $1 break;
  proxy_pass http://yellow_waf;
  proxy_set_header Host $host;
  include waf-internal-proxy-common.conf;
}
```

不得把 `proxy_pass` 改成客户端可控的域名、IP 或 URL。

## 4. 黄 WAF 配置

文件：

```text
/opt/openresty-waf/conf/nginx-yellow.conf
```

两个固定 upstream 当前都指向同一个知识库服务：

```nginx
upstream protected_backend_a {
  server 192.168.14.249:6789;
  keepalive 32;
}

upstream protected_backend_b {
  server 192.168.14.249:6789;
  keepalive 32;
}
```

默认虚拟主机：

```nginx
listen 10.64.9.2:80 default_server;
server_name "";
```

Host A：

```nginx
listen 10.64.9.2:80;
server_name kb.pxsemic.tech;
```

其内部代理必须为：

```nginx
proxy_pass http://protected_backend_a;
proxy_set_header Host kb.pxsemic.tech;
```

Host B：

```nginx
listen 10.64.9.2:80;
server_name kb-1.pxsemic.tech;
```

其内部代理必须为：

```nginx
proxy_pass http://protected_backend_b;
proxy_set_header Host kb.pxsemic.tech;
```

`kb-1.pxsemic.tech` 当前是入口别名，所以发给实际后端的 Host 仍为
`kb.pxsemic.tech`。不要擅自改成 `kb-1.pxsemic.tech`。

## 5. 蓝、黄共同的活动白名单

文件：

```text
/opt/openresty-waf/conf/waf_rules.lua
```

必须直接使用部署包内完整文件。该文件应输出以下五条规则：

```text
ALLOW POST kb.pxsemic.tech   /ai/knowledge/search          [BY-002-KB-SEARCH]
ALLOW GET  kb.pxsemic.tech   /ai/knowledge/assets/{uuid}   [BY-002-KB-ASSET]
ALLOW GET  kb.pxsemic.tech   /ai/knowledge/health          [BY-002-KB-HEALTH]
ALLOW POST kb.pxsemic.tech   /ai/knowledge/graph/query     [BY-002-KB-GRAPH-QUERY]
ALLOW GET  kb.pxsemic.tech   /ai/knowledge/graph/health    [BY-002-KB-GRAPH-HEALTH]
```

`kb-1.pxsemic.tech` 不在活动白名单中，即使 Nginx 已存在该虚拟主机，也必须被七层规则拒绝。

检索请求 JSON 只允许以下字段：

| 字段 | 类型 | 要求 |
|---|---|---|
| `query` | string | 必填；1～4000 字符、最多 16000 字节、非空 |
| `top_k` | integer | 可选；出现时为 1～50 |

图谱查询请求 JSON 只允许：

| 字段 | 类型 | 要求 |
|---|---|---|
| `cypher` | string | 必填；1～20000 字符、最多 80000 字节、非空 |
| `parameters` | object | 可选；接口契约允许动态参数字段 |
| `limit` | integer | 可选；出现时为 1～1000 |

GET 接口不允许请求体。资产详情路径只接受 `/ai/knowledge/assets/` 后紧跟一个规范 UUID。
所有接口继续拒绝 query string 和未知顶层字段。

检索接口允许的上游状态码为：

```text
200 422 502 503
```

其它四个接口因源文档未登记错误响应结构，当前只允许 `200`。成功响应最大 1 MiB，
健康响应最大 16 KiB，检索错误响应最大 16 KiB。上游返回未知状态码、非 JSON、未知字段、
缺少必填字段或类型不一致时，WAF 返回 `502`，不向调用方返回原始上游正文。

以下五处对象按接口文档允许动态字段，规则检查会逐项输出 warning：

```text
results[].metadata
asset.raw_document.metadata
graph request.parameters
graph response.parameters
graph response.rows[]
```

这些动态对象内的字段和值会在请求/响应总大小限制内放行。结构校验不能证明内容已经脱敏，
生产放行前必须确认其跨边界传输已获批准。WAF 只校验 Cypher 字符串长度和顶层结构；
“只读 Cypher”仍须由黄区服务、只读 Neo4j 账号和过程审计共同保证。

## 6. 上线前备份

蓝、黄节点分别执行，只备份自身现有配置：

```bash
WAF_NODE_ROLE='blue'  # 黄节点改为 yellow
WAF_BACKUP_DIR="/root/openresty-waf-conf-backup-$(date +%Y%m%d%H%M%S)-${WAF_NODE_ROLE}"

sudo install -d -o root -g root -m 0700 "$WAF_BACKUP_DIR"
sudo cp -a \
  "/opt/openresty-waf/conf/nginx-${WAF_NODE_ROLE}.conf" \
  /opt/openresty-waf/conf/waf_rules.lua \
  "$WAF_BACKUP_DIR/"
```

保存命令输出中的备份目录，用于回滚。

### 6.1 将部署包文件安装到现有目录

如果采用完整新版本目录切换，解压后的文件已经就位，可跳过本小节。如果现场采用仅替换
配置文件的方式，先把新部署包解压到独立发布目录，再按节点角色安装，不能从旧目录复制。

蓝节点：

```bash
WAF_RELEASE_DIR='/填写新部署包的解压目录/openresty-waf'

sudo install -o root -g nobody -m 0640 \
  "$WAF_RELEASE_DIR/conf/nginx-blue.conf" \
  /opt/openresty-waf/conf/nginx-blue.conf
sudo install -o root -g nobody -m 0640 \
  "$WAF_RELEASE_DIR/conf/waf_rules.lua" \
  /opt/openresty-waf/conf/waf_rules.lua
```

黄节点：

```bash
WAF_RELEASE_DIR='/填写新部署包的解压目录/openresty-waf'

sudo install -o root -g nobody -m 0640 \
  "$WAF_RELEASE_DIR/conf/nginx-yellow.conf" \
  /opt/openresty-waf/conf/nginx-yellow.conf
sudo install -o root -g nobody -m 0640 \
  "$WAF_RELEASE_DIR/conf/waf_rules.lua" \
  /opt/openresty-waf/conf/waf_rules.lua
```

不要把蓝配置装到黄节点的生效文件名，也不要把黄配置装到蓝节点的生效文件名。

## 7. 配置检查

### 7.1 两端规则检查

蓝、黄节点都执行：

```bash
cd /opt/openresty-waf
/data/openresty/luajit/bin/luajit \
  scripts/check_rules.lua \
  conf/waf_rules.lua
```

预期：

```text
0 error，5 warning
白名单条数：5
```

五个预期 warning 是第 5 节列出的动态对象。出现其它 warning 则禁止重载。

然后记录两端规则摘要：

```bash
sha256sum /opt/openresty-waf/conf/waf_rules.lua
```

蓝、黄两端摘要必须完全相同，不同则禁止重载。

### 7.2 黄节点 Nginx 检查

```bash
/data/openresty/bin/openresty \
  -p /opt/openresty-waf/ \
  -c conf/nginx-yellow.conf \
  -t
```

### 7.3 蓝节点 Nginx 检查

```bash
/data/openresty/bin/openresty \
  -p /opt/openresty-waf/ \
  -c conf/nginx-blue.conf \
  -t
```

两项都必须出现 `syntax is ok` 和 `test is successful`。

## 8. 重载顺序

先黄后蓝：

```bash
# 黄节点
sudo systemctl reload openresty-waf@yellow
sudo systemctl status openresty-waf@yellow --no-pager

# 黄节点成功后，再在蓝节点执行
sudo systemctl reload openresty-waf@blue
sudo systemctl status openresty-waf@blue --no-pager
```

任一节点配置检查或重载失败，都不要继续下一节点。

## 9. 调用方式

正式 DNS 应将两个业务 Host 解析到蓝 WAF `10.64.5.4`。调用方不要再使用
`192.168.14.249:6789`。

DNS 已生效时：

```bash
curl -i \
  http://kb.pxsemic.tech/ai/knowledge/search \
  -H 'Content-Type: application/json' \
  --data '{
    "query": "ASML 通信异常怎么排查",
    "top_k": 5
  }'

curl -i \
  http://kb.pxsemic.tech/ai/knowledge/assets/f440c18e-a281-44bc-a878-8aa92b620879

curl -i http://kb.pxsemic.tech/ai/knowledge/health

curl -i \
  http://kb.pxsemic.tech/ai/knowledge/graph/query \
  -H 'Content-Type: application/json' \
  --data '{
    "cypher": "MATCH (e) WHERE toLower(e.name) CONTAINS toLower($entity) RETURN e LIMIT $limit",
    "parameters": {"entity": "ASML", "limit": 10},
    "limit": 10
  }'

curl -i http://kb.pxsemic.tech/ai/knowledge/graph/health
```

DNS 未生效时，用 `--resolve` 测试，不要直接把 URL 改成 IP：

```bash
curl -i \
  --resolve kb.pxsemic.tech:80:10.64.5.4 \
  http://kb.pxsemic.tech/ai/knowledge/search \
  -H 'Content-Type: application/json' \
  --data '{
    "query": "ASML 通信异常怎么排查",
    "top_k": 5
  }'
```

其它四个接口同样在 URL 前保留 `--resolve kb.pxsemic.tech:80:10.64.5.4`。

将命令中的 Host 替换为 `kb-1.pxsemic.tech` 是拒绝用例，不能作为合法调用方式。

## 10. 验收用例

至少执行以下用例：

| 用例 | 预期 |
|---|---|
| `kb.pxsemic.tech` 分别调用五个合法接口 | 到达后端并返回符合各自 schema 的 JSON |
| `kb-1.pxsemic.tech` 发送相同请求 | `403 not_in_whitelist` |
| URL 使用 `10.64.5.4` 且不设置业务 Host | 默认虚拟主机拒绝，通常连接无响应或状态为 `000` |
| Host 使用 `192.168.14.249` | 拒绝 |
| 请求增加未知字段 | `400 request_body` |
| 检索请求缺少 `query` | `400 request_body` |
| 检索请求增加 `include_graph` | `400 request_body` |
| 图谱查询 `limit=1001` | `422 request_body` |
| 资产 ID 不是 UUID | `403 not_in_whitelist` |
| UUID 后增加额外路径层级 | `403 not_in_whitelist` |
| 将任一接口改为未登记方法 | `403 not_in_whitelist` |
| 路径后增加 `/` | `403 not_in_whitelist` |
| 增加任意 query string | `403 query_not_allowed` |
| 新增接口上游返回未登记状态码 | WAF 返回 `502 response_status_not_allowed` |

蓝、黄节点分别检查：

```bash
sudo tail -n 20 /data/openresty-waf/audit/access.log
sudo tail -n 20 /data/openresty-waf/audit/rejected.log
```

合法请求应能在两端用同一 `trace_id` 关联，并看到正确的 `rule_id`、Host、path、
上游地址和响应状态。

## 11. 回滚

如重载后异常：

1. 先停止或摘除蓝端入口流量；
2. 先恢复黄节点备份的 `nginx-yellow.conf` 和 `waf_rules.lua`；
3. 黄节点配置检查通过后重载黄节点；
4. 再恢复蓝节点备份的 `nginx-blue.conf` 和 `waf_rules.lua`；
5. 蓝节点配置检查通过后重载蓝节点；
6. 验证旧业务恢复后再恢复入口流量。

不要删除失败版本配置和审计日志，保留用于排查。

## 12. 仍需上线前确认的外部控制

本仓库只实现七层 WAF。正式放行前仍需确认：

- 四层 ACL 只允许登记来源访问蓝 WAF，并只允许蓝 WAF 访问黄 WAF；
- 黄 WAF 端口不接受其它来源，后端不能被跨区调用方绕过 WAF 直连；
- 合法业务 Host `kb.pxsemic.tech` 只解析到蓝 WAF；
- 来源系统身份、owner、QPS、审批单和有效期已经登记；
- 黄区知识内容符合数据分级和脱敏要求；
- 审计日志轮转、留存、防篡改转储和敏感正文处置方案已经确认。
